本轮决定为 `proceed_to_forward_review`；第二轮人工决定已经转化为 11 个 Gold、11 个 Rejected 和 1 个 Candidate，新规则已经覆盖主语归属、空行、原始材料呈现、行内代码和渲染器对齐能力

## 2. 为什么旧通过结果不足

旧检查曾以 `160/160`、`22/22`、`18/18` 和 `6/6` 全部通过，但用户仍发现主语不明确、空行过多、题注没有居中和引用块用途不清

形成这一冲突的直接原因是旧检查没有对应字段与正反例；实际影响是旧结果只能证明旧合同内部一致，不能用于推断自然表达已经合格；本轮因此增加合同字段、16 个确定性正反例、12 个语境案例和两轮未见前向测试，而没有继续扩大单词禁用规则

## 4. 外部依据

- npm 官方规则要求品牌名称保持小写，并明确禁止把 npm 当作首字母缩写解释；这直接否定了 `NPM（Node Package Manager）` 修复方案，同时允许在首次出现后添加 `package manager` 等通用类别，来源见 [npm Logos and Usage](https://docs.npmjs.com/policies/logos-and-usage/)
- CommonMark 把引用块定义为以 `>` 标记的块级内容；本项目据此只用引用块保存需要逐字核对的短原文，不用它包装生成结论，来源见 [CommonMark 规范](https://spec.commonmark.org/)
- GitHub 原生支持在 Markdown 中渲染 Mermaid，但最终位置与布局仍受渲染器控制；本项目因此区分“请求居中”和“渲染器能够精确保证居中”，来源见 [GitHub 创建图示文档](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)

## 5. 本轮设计决定

第一项决定是主语明确性保持语境规则；独立动作、主体切换和可能歧义的位置需要补出主体，相邻内容保持同一主体时允许自然省略；原因是逐句强制主语会产生新的机械文体

第二项决定是连续两个以上空行属于确定性错误，同一列表项目保持连续；是否另起段落仍由主题变化判断；原因是空行数量可以机械确认，主题边界不能只靠固定句数判断

第三项决定是对象和题注默认请求居中，同时记录渲染器能力；HTML、Word 和 PDF 可以精确控制，GitHub 原生表格与 Mermaid 可能只能保留默认布局并登记限制；原因是系统不能把渲染器没有提供的能力伪报为成功

第四项决定是已接受 R2 不做追溯格式修订；空行、分号、题注和局部标记意见进入 `non_blocking_preferences`；原因是用户接受绑定的是精确正文，后续修改必须形成新候选

## 6. 防过拟合边界

第一轮 20 个前向请求没有使用首批锚点中的 npm、CI、FPGA、幂等键、PowerShell、SHA-256、订单、发票和队列材料；生成 Agent 不能读取 Gold、Rejected、语境案例、验证器、评分标准或本对话历史

这些隔离措施只能降低定向修补风险，不能单独证明泛化；最终判定仍需要用户逐项审核，并且第一轮至少接受 18/20、事实硬错误为 0，才允许生成第二轮 20 个未见案例

## 7. 剩余风险与停止条件

- `CANDIDATE-03-R3` 仍是 Candidate；原因是自动检查不能代替用户对主语和 npm 解释的阅读判断；影响是首批锚点尚未达到 12/12 Gold
- 第一轮未见案例尚无人工结果，并且已经发现 3 个中文句号硬错误；原因是候选刚完成首次生成且隔离 Agent 未稳定遵守标点配置；影响是当前泛化接受率未知，本轮已经不能满足硬错误为 0 的标准
- 第二轮未见案例尚未生成；原因是计划要求第一轮通过后才能继续；影响是无法提前宣称连续两轮达到 90%
- GitHub 原生 Markdown 不能可靠控制所有对象居中；原因是布局由渲染器决定；影响是发布前必须分别检查桌面和移动端呈现，并诚实记录无法保证的位置

在 C03-R3 与两轮未见测试全部通过以前，`main` 保持冻结，本机正式 Skill 不安装候选版本，项目状态只能写成“候选等待人工审核”
