# vNext 1.1 第三轮收敛与泛化验证修正案

## 1. 决定来源

本修正案保存第一轮 20 个未见前向案例的用户审核结果；原始成绩为 8/20，实际接受率为 40%，原因是 12 个答案仍然出现术语解释、排比结构、GitHub 居中、代码覆盖和多轮替换问题

修订版属于学习样本，不替换第一次未见测试成绩；第二轮在 13 个当前 Candidate 全部获得用户接受以前保持停止

## 2. 生命周期变化

本轮完成以下状态转换：

* `CANDIDATE-03-R4` 转为 `REJECTED-03-R4`
* 新建 `CANDIDATE-03-R5`
* 第一轮 8 个原样接受答案转为 Gold
* 第一轮 12 个未接受答案转为 Rejected
* 12 个修订答案以 R2 版本进入 Candidate

转换完成后共有 57 个生命周期记录：

* Gold：19 个
* Rejected：25 个
* Candidate：13 个

每个已审核答案绑定精确摘要；修订候选使用新版本号，禁止覆盖原始答案或改变第一轮成绩

## 3. 通用合同变化

任务合同增加以下结构：

* `term_requirements`：登记官方英文、缩写、名称含义和名称依据
* `structure.parallel_groups`：登记两个以上承担相同作用的平行项目
* `code.coverage_mode`：区分合法代码注释与逐行独立解释
* `conversation.preserve_superseded_requirements`：决定是否保留已经失效的旧要求
* `presentation.render_evidence`：登记 GitHub 桌面、移动端、亮色和暗色实际渲染结果

验证包增加排比覆盖账本和代码单元映射；程序只检查 Agent 已登记的结构，不使用正则表达式单独决定自然语言是否构成排比

## 4. npm 规则

生成正文保持官方小写 `npm`；首次出现时自然说明它是 Node.js 生态使用的包管理客户端和软件包仓库

以下形式继续阻断：

* `Node.js Package Manager`
* `Node Package Manager`
* `包管理器（Package Manager）`

阻断原因是这些形式会把官方名称误当成首字母缩写，或者把通用类别放进括号造成阅读歧义

## 5. 前向报告接口

第一轮报告拆成三个独立结果：

* `artifact_integrity`：检查请求、答案、摘要、来源和组件是否保持完整
* `human_acceptance`：记录用户原样接受数量和实际比例
* `next_round_allowed`：说明是否达到生成下一轮的条件

该结构禁止出现顶层 `PASS` 与内部轮次失败互相矛盾的结果

## 6. 当前停止条件

当前状态固定为：

`vNext 1.1 候选版本正在根据第一轮前向测试修订，泛化能力尚未通过验证`

只有 13 个修订候选全部获得用户接受后，系统才允许生成第二轮 20 个全新案例
