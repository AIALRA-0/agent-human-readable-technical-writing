# 轻量可适应的 Agent 写作风格方案

## 整体综述

> 你现在遇到的主要问题不是规则太少，而是规则容易膨胀成重型门禁，我会把写作层改成轻量的建议、按需模板和最小自查，让 Agent 更快地产出，同时保留你真正需要的逻辑链和信息完整性

- 当前糟糕体验：当前已有许多有效偏好，包括问题到完成状态的逻辑链、中文排版、术语解释、来源边界和局部修复，但这些要求的强弱层级与触发条件还没有被统一表达
- 核心堵点或总体风险：如果把所有偏好都写成硬规则，Agent 会增加无意义的解释、重复复核和整段重写，如果放得过松，又可能丢失事实、条件、数字、来源或用户真正需要的下一步
- 我准备改变什么：我会建立一层默认轻量的写作配置，把规则分成建议、适应和必要检查三类，并用渐进展开、单元级逻辑链和一次默认自查控制复杂度
- 你最终得到什么：你看到的普通答案会先给结论和必要背景，复杂任务会清楚说明为什么、改变什么、怎么验证和如何收尾，Agent 可以按场景调整表达，不需要为每句话运行沉重流程

## 问题单元 1：边界和强弱分层

先确定哪些内容是写作建议，哪些内容需要按场景适应，哪些内容只涉及事实完整性或安全边界

> 你需要先把写作引导的边界说清楚，我会把表达偏好和事实保护分开，避免规则继续膨胀成门禁

### 这一个问题你需要知道

- 为什么要做：如果不先分层，后面的模板和自查很容易把普通文风当成失败条件，速度和 Agent 自由度都会下降
- 现在发生了什么：当前规则分散在 Skill、配置、设计和测试中，已有有效要求，但强制程度、触发条件和排除范围没有统一入口
- 现在要改变什么：我会建立建议、适应和必要检查三层，并明确不做逐句门禁、固定句长门禁、自然度门禁和外部系统改造
- 有没有阻断或风险：主要风险是漏掉你反复强调的隐性偏好，或者为了完整盘点而引入新的重型流程
- 需要你批准什么：请你只批准本地写作层的规则分层，发布、安装、外部 Agent 和其他项目不包含在这次授权里
- 什么结果算成功：每条规则都有强度、适用范围、触发条件和退出方式，普通表达可以自然完成，事实和来源完整性仍然有保护
- 出错以后怎么办：如果分层造成遗漏或过度限制，只回退争议条目和对应模板，不重写整个 Skill

### 需要你核对

1. 这一单元决定哪些规则能影响 Agent 的自由度，你希望采用哪种边界，这会直接影响速度和稳定性
   - A：建议优先，只对事实、来源和明确格式合同做必要检查，运行最快
   - B：建议加少量结构检查，换取更稳定的计划和报告形状
   - C：先不改现有边界，暂停这部分方案
   - D：我来指定其他边界和例外

## 问题单元 2：内容单元级逻辑链

把问题到完成状态的关系放进可独立理解的内容单元，而不是把同一套标签重复贴到每一句话

> 你希望每段重要说明都能回答为什么、做什么和如何收尾，我会用内容单元承载这条链，保持短答案仍然自然

### 这一个问题你需要知道

- 为什么要做：你现在最难读的是计划只给决策和任务，读者看不到原因、验证、证据和完成标准，但逐句展开又会变得臃肿
- 现在发生了什么：已有问题、需求、决策、任务、验证、证据和完成状态这条明确思路，但缺少短内容和复杂内容的共同使用方式
- 现在要改变什么：我会为计划、报告、解释、翻译和改写提供最小模板，并允许短内容合并字段、取消标题或只保留真正有用的链条节点
- 有没有阻断或风险：主要风险是模板化重复，尤其把每句话都写成同样的七段结构后，结论会被结构淹没
- 需要你批准什么：请你批准逻辑链按内容单元落地，不要求每句话都显式出现七个标签，也不把模板格式当成普通写作门禁
- 什么结果算成功：读者能在每个重要单元中找到问题、目标、决定、动作、验证、证据和完成状态，短任务不会被无关说明拖长
- 出错以后怎么办：如果样例出现重复或遗漏，只调整命中的单元模板和省略规则，保留原有事实与来源映射

### 需要你核对

1. 这一单元决定逻辑链出现到什么粒度，你希望怎样平衡可读性和完整性
   - A：按独立问题或阶段呈现，短内容可以合并字段，最符合快速阅读
   - B：按每个段落呈现，结构更明显但篇幅和重复会增加
   - C：暂不建立统一模板，先保持自由写作
   - D：我来指定其他粒度或省略规则

## 问题单元 3：渐进展开和性能

让默认回答保持最小充分说明，在长文本、高风险、歧义和用户明确要求下再增加背景、术语和证据

> 你希望质量提高但不要牺牲速度，我会让 Agent 默认走短路径，只有确实需要时才展开解释和复核

### 这一个问题你需要知道

- 为什么要做：所有任务都加载完整规则、术语卡和多轮自查会浪费 Token，也会让简单问题失去清晰度
- 现在发生了什么：当前很多要求没有统一触发条件，Agent 可能在简单回答中过度解释，也可能在复杂回答中解释不足
- 现在要改变什么：我会按任务长度、风险、受众、歧义和用户请求设置展开条件，并先测现有基线再决定合理开销
- 有没有阻断或风险：主要风险是轻量化过度，导致用户仍然不知道为什么、影响是什么或下一步怎么做
- 需要你批准什么：请你批准渐进展开作为默认策略，性能目标先以可测基线为依据，不预设无法证明的绝对速度承诺
- 什么结果算成功：短任务保持短，复杂任务在需要的位置补足背景和证据，额外 Token、延迟和复核次数都有记录且没有无意义增长
- 出错以后怎么办：如果默认路径遗漏理解所需内容，只调整触发条件或展开层级，不把所有回答永久升级为长格式

### 需要你核对

1. 这一单元决定什么时候增加说明，你更看重哪种取舍，这会影响输出长度和理解可靠性
   - A：默认最小充分说明，长、高风险或歧义任务才展开，性能优先
   - B：默认多给背景和证据，阅读更稳但输出更长
   - C：先不设置触发策略，暂停性能方案
   - D：我来指定触发条件和性能上限

## 问题单元 4：术语的按需解释

首次出现时给出读者能继续阅读所需的最小定义，完整关系和背景放入可复用的扩展术语卡

> 你希望陌生术语真正讲明白，但不希望每个词都占满正文，我会把必要定义留在正文，把深度信息放到按需展开层

### 这一个问题你需要知道

- 为什么要做：完整术语字段对关键概念很有价值，但对普通词语全部展开会增加篇幅、索引成本和重复解释
- 现在发生了什么：已有中文名、官方英文、缩写、机制、用途、层级、优劣和示例等丰富要求，但正文最小字段与扩展字段尚未分开
- 现在要改变什么：我会定义最小首次解释、扩展术语卡、唯一索引和冲突复核，已登记术语优先复用而不是重新生成
- 有没有阻断或风险：主要风险是术语卡与正文出现不同定义，或者没有界面支持时强行设计悬浮交互
- 需要你批准什么：请你批准先以纯文本和 Markdown 可用为最低方案，侧边栏、悬浮卡和知识图谱只作为以后可选增强
- 什么结果算成功：读者首次遇到关键术语时能继续理解，官方名称和缩写不丢失，普通术语不会被迫展开全部背景
- 出错以后怎么办：发现术语冲突时冻结该条目，只修正冲突字段和首次出现位置，无法确认官方写法就转人工复核

### 需要你核对

1. 这一单元决定术语信息放在哪里，你希望怎样兼顾理解深度和正文速度
   - A：正文给最小定义，完整背景按需展开，兼容性和速度最好
   - B：正文直接给完整术语卡，理解集中但篇幅明显增加
   - C：只保留用户指定术语，其他术语不主动扩展
   - D：我来指定哪些术语必须展开以及展开位置

## 问题单元 5：媒介感知的呈现

把普通正文的表达偏好与代码、日志、引文、表格等不可改写区域分开，再根据实际媒介选择呈现方式

> 你希望同一份内容在聊天、Markdown 和代码混合场景里都清楚，我会让呈现规则随媒介变化，同时保护原文区域不被改写

### 这一个问题你需要知道

- 为什么要做：普通中文、逐字引文、日志和代码的正确格式不同，强行使用一个模板会损害信息或增加无效处理
- 现在发生了什么：已有中文标点、英文大小写、列表缩进、引用块、代码块和行号等偏好，但保护区域与降级方式还不够统一
- 现在要改变什么：我会登记媒介规则、原文保护边界和最低兼容面，富界面能力只在实际存在时增强，不把它当成运行前提
- 有没有阻断或风险：主要风险是格式化流程改变代码、日志、数字或逐字引文，或者不同客户端让用户看到不一致的结果
- 需要你批准什么：请你批准以可读纯文本和 Markdown 作为最低兼容面，界面增强不纳入本次写作层实施范围
- 什么结果算成功：用户能快速区分正文、引用、代码、日志和表格，关键事实在不同媒介保持一致，原文区域没有被改写
- 出错以后怎么办：如果渲染造成漂移，恢复原文保护区域和上一版呈现规则，只修复发生问题的媒介适配层

### 需要你核对

1. 这一单元决定没有富界面能力时如何呈现，你希望怎样处理兼容性和视觉增强的取舍
   - A：纯文本和 Markdown 保证可用，行号和悬浮信息作为可选增强
   - B：优先设计富界面交互，纯文本只作为降级方案
   - C：暂不扩展媒介规则，只保留当前基础格式
   - D：我来指定每种媒介的最低和增强能力

## 问题单元 6：带上下文的提问

在用户需要选择时补足问题背景、选择影响、推荐默认和示例，但不把问答模板插入不需要对齐的普通回答

> 你不想再面对看不懂的单行选择题，我会让 Agent 先说明选择会改变什么，再给有限选项和自定义入口

### 这一个问题你需要知道

- 为什么要做：如果用户不了解背景和后果，选项再规范也只是盲选，后续计划可能从一开始就偏离
- 现在发生了什么：当前提问往往只有一句选择请求，缺少上下文、推荐理由、例子和不选择的影响
- 现在要改变什么：我会提供短版和展开版提问模板，只有选择会改变范围、风险、成本或结果时才增加说明
- 有没有阻断或风险：主要风险是模板本身变成长前言，或者推荐默认被误解为替用户做决定
- 需要你批准什么：请你批准上下文提问作为按需工具，不要求所有普通对话都先走固定问答流程
- 什么结果算成功：用户能复述问题、选项差异和推荐影响，遇到不同需求可以用自定义入口，不会因为模板增加不必要等待
- 出错以后怎么办：如果问题仍然看不懂，只补充造成误解的背景和影响，不重新设计整个提问系统

### 需要你核对

1. 这一单元决定 Agent 什么时候需要解释选项背景，你希望怎样减少盲选同时控制提问长度
   - A：涉及范围、风险或结果变化时展开背景，普通问题保持简短
   - B：所有选择题都展开背景和示例，理解优先但交互更慢
   - C：继续使用简短选择题，只有用户追问时再解释
   - D：我来指定需要展开背景的问题类型

## 问题单元 7：一次默认自查和升级路径

让 Agent 在输出后重读适用规则并做最小自查，问题清零就结束，只有风险或明确发现才进入局部修复或人工复核

> 你希望看到的是干净 Agent 自己读规则并完成闭环的结果，我会保留一次默认自查，但不让复核循环吞掉主体工作

### 这一个问题你需要知道

- 为什么要做：没有输出后复查，明显的标点、结构和事实遗漏容易留下，有无限复查又会造成重复劳动和整段改写
- 现在发生了什么：当前已有许多测试和迭代想法，但普通使用、自查、模型评估和用户接受之间的职责边界还需要轻量化
- 现在要改变什么：我会规定生成、重读、一次检查、局部修复和必要升级的顺序，并把自动通过与用户接受分开记录
- 有没有阻断或风险：主要风险是自查被误当成写作门禁，或者 Agent 用反复重写掩盖没有定位清楚的问题
- 需要你批准什么：请你批准一次默认自查和有限升级路径，不批准无条件的多模型矩阵、长时间循环或自动金标
- 什么结果算成功：普通任务一次检查即可结束，发现问题时能定位并做最小修改，无法安全修复时明确交给人工，不伪造通过或接受
- 出错以后怎么办：三次局部修复仍不能清零就停止并标记需要人工复核，保留初稿、发现、补丁和复验摘要

### 需要你核对

1. 这一单元决定输出后复核有多重，你希望怎样平衡质量证据和执行速度
   - A：一次默认自查，只有发现问题或高风险任务才增加局部修复
   - B：每次都运行多轮语义复核，证据更丰富但速度和 Token 成本更高
   - C：不在普通使用中自查，只在专门评测时检查
   - D：我来指定任务类型、复核轮数和停止条件
