# 用户金标规则

## 1. 最终标准

用户明确审核通过的版本才是风格金标；脚本通过、模型评分和 Agent 自评只能提供辅助证据

## 2. 案例状态

- `candidate`：由 Codex 生成，等待用户审核
- `gold`：用户明确接受，并记录接受依据
- `rejected`：用户明确拒绝，并记录具体问题
- `hidden`：用于检查系统是否只记住可见模板；运行中的写作 Agent 不读取参考答案

## 3. 状态转换

候选案例只能在用户明确审核后转换：

- 用户接受时，复制到 `evals/gold/`，写入 `approved_by_user: true` 和审核记录
- 用户拒绝时，复制到 `evals/rejected/`，写入拒绝原因和需要保留的正确部分
- 用户要求修改时，原候选保留历史，新版本使用新的修订号

Agent 不得自行修改 `approved_by_user`，也不得用模型投票替代用户确认

每次审核记录当前配置修订号和答案摘要；用户接受只绑定当时看到的精确正文，后续格式改动必须形成新候选，不能覆盖已经接受的快照

同一锚点可以保留多个版本化拒绝记录，例如 `REJECTED-03` 和 `REJECTED-03-R2`；历史拒绝原因不得被后续版本覆盖

用户明确表示不影响接受的偏好进入 `non_blocking_preferences`；这些偏好指导后续生成，但不反向改写已经接受的 Gold

## 4. 隐私边界

案例只使用用户明确允许公开的片段、公开资料或合成材料；账户信息、私有路径、原始会话和未授权文本不能进入公开仓库

## 5. 首批停止条件

12 个候选锚点形成以后停止扩展运行时和测试规模；只有用户完成审核，系统才能根据真实接受与拒绝样本继续实现下一阶段

## 6. 前向测试

前向案例使用首批锚点没有出现的来源、术语和领域；生成 Agent 只能获得原始请求和当前 Skill，不能获得预期答案、怀疑问题或拟议修复

每个前向答案只生成一次并绑定摘要；用户看到以前不得针对已知评分项重写，自动检查只负责事实、来源、结构和隐私硬门

连续两轮各 20 个未见案例达到至少 18 个用户接受，并且事实、条件、范围、来源、原文覆盖和新增事实硬错误均为 0，才能把泛化状态标记为达到当前发布门
